Making a Portfolio Agent-Ready: llms.txt, MCP and WebMCP

  • MCP
  • AI Agents
  • Cloudflare Workers
  • Architecture

A visitor to this site is no longer always a person with a browser. Sometimes it is an assistant that wants to answer "what has this engineer built?" without scraping a page. In November 2026 I spent a week making the site easier for those readers, and this is what changed and what surprised me.

Where it started

An agent-readiness scan scored the site 3 out of 5. The pages were fine for people; for software there was no map of the content, no way to ask a question, and the CDN was blocking AI crawlers before they reached a single file. A re-scan after the work scored 4. The checks that still fail are the ones that do not apply here, such as OAuth discovery, because nothing on the site needs a login.

What I built

  • A map to read first. /llms.txt lists the projects, posts and work history as Markdown links. It is generated from the same JSON files as the pages, so it cannot drift.
  • A clear crawl policy. robots.txt says AI training crawlers are welcome, with Content Signals that state it in a machine-readable way. This was a decision, not a default: I would rather be in the answer than absent from it.
  • A read-only MCP server. The same Cloudflare Worker that serves the live widgets now answers at /mcp. Its tools return the profile, projects, work history, posts, recent GitHub activity and site health numbers. Every tool only reads, and each says so in its annotations.
  • In-page tools. Browsers that support WebMCP get five tools registered from the page itself. The contact tool fills in the form but never sends it.
  • Discovery documents. An API catalog, an MCP server card and an agent skill live under /.well-known/, so a client can find all of the above from the domain name alone.

What surprised me

  • Cloudflare adds its own robots.txt block only while some AI policy is set to block. Once every policy allowed training, the block disappeared, and so did my Content Signals until I moved them into the file in the repository.
  • Adding an MCP handler took the Worker from about 15 KiB to about 1.25 MiB. It still starts fast, but it is a number I now watch.
  • The service worker answered any unknown same-origin request from its cache, which would have served stale API and MCP responses. It needed an early return.
  • GitHub Pages cannot send an extensionless file as application/linkset+json, so the Worker serves the discovery documents on narrow routes.

Use it from Claude

The server needs no sign-in. In Claude, add it as a custom connector (Settings, Connectors, Add custom connector) with the address https://andernet.dev/mcp and sign-in off. In Claude Code, run claude mcp add --transport http portfolio https://andernet.dev/mcp. Then ask it about the projects, the posts or how the site is doing.

None of this uses a model at the moment a visitor loads a page. The site stays static where it can be, and the agents bring their own.
